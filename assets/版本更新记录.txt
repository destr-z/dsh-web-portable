 DSH Web 便携版 · 版本更新记录
========================================

记录规则：
  · 每个版本一节，新的在上。
  · 版本号规则 主.次.修订：
      主  → 底层 DSH 换代（例如 0.1.5 → 0.2.0）或界面发生大改
      次  → 新增能力（新插件、新启动器功能）
      修订→ 只修问题，不加新东西
  · 每节必须写清：日期、包内 exe 的 SHA256、改了什么、已知问题。
    换过 exe 就必须更新 SHA256，否则没法核对别人手上那份到底是哪版。

  powershell -Command "(Get-FileHash '程序\deepseek-harness.exe' -Algorithm SHA256).Hash"
  与本节记录的 SHA256 对比，不一致就不是同一版。

【v2.0.2】2026-09-28  ·  修「设置被启动器覆盖」与「会话恢复失败」（重建 exe）
========================================

■ 一句话

  · **你的设置不再被启动器覆盖**。模型渠道（中转站那几条）、默认模型、主题、各插件配置
    都存在 `profiles\web\cordis.patch.yml` 里，而旧启动器**每次启动都整份重写**它 ⇒
    界面里配好的渠道下次启动就没了（实测：便携版数据目录里连一丝痕迹都不剩）。
    本版起：该文件**已存在就只补启动器自己缺的那几段，其它一个字节都不动**；
    要补写时先备份 `cordis.patch.yml.bak-launcher-<时间戳>`（保留最近 3 份）。
  · **会话恢复不再失败**。单文件 exe 里 worker 线程读不到快照路径：
      Cannot find module 'C:\snapshot\…\dsh-session-persistence-jsonl\lib\worker.cjs'
    于是「打开已有会话 / 选模型」直接报 `gateway/internal: resume failed …`。
    本版给验证器加了兜底：worker 起不来就退回**进程内验证**（算法完全一致，
    只少了"新 isolate"这层加固；验证结论本身照旧抛出）。

■ 为什么会这样

  · 设置被覆盖：这个 patch 文件过去是启动器的"自留地"，整份重写既省事又天然幂等。
    但 0.1.7 起**设置服务也往同一个文件里写**（便携版那份里出现
    `ui-settings-general` / `external-ui-skin` 的 `config` 就是证据）。两个写入者
    共用一个文件之后，"整份重写"就变成了数据丢失。
    注意：**不能改成简单追加** —— 程序生成的空模板结尾是 `[]`，已经结束了整个 YAML 文档，
    在它后面追加 `- id: …` 会变成两段顶层数组、解析直接失败。所以分两种情形：
    空模板 → 整份写模板；已有内容 → 只补缺的段。
  · 会话恢复：`@yao-pkg/pkg --sea` 把模块放进虚拟快照 `C:\snapshot\…`，主进程的 fs 与
    模块解析被 pkg 打过补丁，但 **Worker 线程里那套补丁不生效** ⇒ 找不到 `worker.cjs`。
    这是打包形态的固有限制，只能在代码里绕过去。

  启动 DSH Web.cmd / 诊断.ps1 / 使用说明.txt       未换
  插件\（5 个）/ notices\                          未换（与 v2.0.1 相同）
  版本更新记录.txt                                本文件

【v2.0.1】2026-09-28  ·  修掉「设置 ▸ 插件」里的元信息错误红字（重建 exe）
========================================

■ 一句话

  v2.0.0 换上 0.1.7 内核后，「设置 ▸ 插件」里三个实验性插件（智能体团队 / 自动授权审查 /
  语音输入）下面各有一行红色 `元信息错误: … icon.svg: ENOENT`。本版修掉它。
  这是**显示层**的问题：那三个插件照常能启用、能运行（内核文档明确写着"元信息诊断不改变
  启停状态或 fiber 阶段"）。

  同一批还修掉另一处「显示层」问题：随包的 5 个插件（剧本批注 / 提示词对照 / 人设切换 /
  皮肤 / 小鲸鱼）**一直不出现在插件面板里** —— 启动器只把它们登记成"参与装配的层"
  （`dsh.profile.bundles`），没登记成 profile 的依赖，而面板恰是按依赖判定"装过没有"。

  还有第三处：**人设切换 / 皮肤 这两个插件的宿主半边在便携版里根本没激活**
  （`failed to import`）—— 面板里那两行显示「未运行」、「皮肤」也不会生效
  （`body` 上没有 `data-dsh-ui-skin` 标记）。原因与修法见下面单独一节。

  第四处：**便携版打开后不再自动弹出网页**。单文件 exe 里"打开默认浏览器"这一步会
  **静默失败** —— 连 `could not open the default browser` 都不打印，而启动器原来的兜底
  恰恰只在读到这句话时才动手，于是既不弹窗、也不兜底。现在改成：启动器给 exe 传
  `--no-open`，自己拿到带 token 的地址后 `Start-Process` 打开（用户显式传 `--no-open`
  时保持不打开）。实测：exe 命令行确实带上 `--no-open`，启动后约 4 秒拉起新浏览器进程。

■ 原因（出在单文件 exe 的资产打包清单）

  · 便携版把内核「烤」进单文件 exe：打包时只把**匹配资产通配清单**的文件放进快照，
    运行时挂载为 `C:\snapshot\<仓库目录名>\…`。
  · 那三个插件的 `package.json` 里声明了 `"icon": "./icon.svg"`，而清单里**没有任何 svg 通配**
    → 图标没进快照 → 运行时 `realpath()` 找不到 → 每个条目一行红字。
  · **源码方式运行的开发版没有这个问题**：它读磁盘上的真实文件，不受快照清单影响。
    v1.5.0（0.1.5 内核）也没有，因为那三个插件与 `icon` 元数据是 0.1.6 / 0.1.7 才有的。
  · 便携包自带的 5 个插件都没有声明 `icon`，所以它们不受影响。

■ 修法

  内核构建脚本 `scripts/build-exe-for-python-sdk.ts` 的 `ASSET_GLOBS` 一次补齐资产类通配：
  `svg / png / ico / woff / woff2 / ttf / css`（原始文件合计约 2.7 MB；SEA 里压缩存放，
  exe 只涨了约 0.2 MB）。这处属于**上游该修**的东西，本地先补上。

■ 随包插件为什么一直不在插件面板里（本版一并修掉）

  · 插件面板的过滤器只列"**在 profile 的 `dependencies` 里**（= 用户装过）"或
    "部署随附的可选官方包"或"读取出错"的组合包（内核 `ui-plugin-manager`：
    `pkg.installed || pkg.optional || pkg.error`）。
  · 便携版启动器此前只把随包插件写进 `dsh.profile.bundles`（决定"要不要加载"），
    `dependencies` 一直留空 —— 于是插件**正常工作、侧栏入口也在**，却从面板里消失，
    也没法在那里启停或打开它们的配置页。开发版没有这个问题，因为它的 profile
    依赖里本来就有那几个 `link:` 条目。
  · 修法：启动器在同步 `bundles` 的同时**同步 `dependencies`**（写包清单里的版本号），
    摘除规则与 `bundles` 完全一致（只碰本启动器管着的东西，用户自己装的绝不碰）。
    离线测试补了对应断言（首启写上、删插件摘掉、清空摘掉、记账丢失也能靠 junction
    形态摘掉、用户自己的包绝不写进去），并顺手把那句写死的"正好 4 条"改成
    **从 `插件\` 现算**（v1.4.0 加了皮肤插件后它就是过时断言了）。

■ 两个通用插件的宿主半边在便携版里 failed to import（本版一并修掉）

  · 症状：启动日志 `3 entries did not activate`，其中 `persona-switcher` 与
    `external-ui-skin` 两行写着 `failed to import`（第三行是官方的 office-to-pdf，见"已知问题"）。
    插件面板里那两行显示「**未运行**」，皮肤也不生效 —— 但客户端半边照常加载，所以
    "看起来装了、其实没跑"，很难发现。
  · 原因：这两个插件的宿主半边 import 了一个便携版运行时**没有的包名**：
      - `dsh-persona-switcher` import 的是 registry 上的**裸名 `schemastery`**，
        而内核提供的是 **`@deepseek-ai/schemastery`**（vendor 的那份）；
      - `dsh-ui-skin` import 的虽是作用域名，却**没把它声明成 peer** ——
        便携版里外部插件只按"自己声明的 peer"从运行时取依赖，没声明就取不到。
    开发版不暴露这个问题：那里的 workspace 两种名字都在。
  · 修法（插件侧）：两个插件统一改用并声明 **`@deepseek-ai/schemastery`**
    （源码 import、`peerDependencies`、构建脚本里的链接名一起改），重新构建后同步进包。
    实测验证：失败列表从 3 条降到 1 条（只剩 office-to-pdf），启动日志里出现
    `[ui-skin] 素材目录：…`（宿主半边跑起来了），`body` 上出现
    `data-dsh-ui-skin="deepseek"`（皮肤真的生效了），控制台 0 错误。
  · ⚠️ **给以后加插件的规则**：便携版里外部插件的 import 必须用**内核的 `@deepseek-ai/*` 名字**，
    并把这些包写进自己的 `peerDependencies`；用 registry 裸名会在便携版里静默变成「未运行」。
  · 附带发现（未修，属于插件仓库自身）：`dsh-ui-skin/scripts/smoke-client.mjs` 还是按 0.1.5
    的 `settingsScope` API 写的（现在 24 项失败），需要按 `configForms` 更新。

【v2.0.0】2026-09-28  ·  内置内核换代：0.1.5-rc.2 → 0.1.7-rc.2（重建 exe）

■ 一句话

  便携版里那个单文件主程序**换了内核**：从 0.1.5-rc.2 升到 0.1.7-rc.2（官方 `dsh-v0.1.7-rc.2`，
  含 0.1.6 那一代的变化）。跟着一起换的还有**两个通用插件**（人设切换 / 皮肤）——
  它们原来调用 0.1.5 的设置服务 `settingsScope`，而 0.1.7 换成了 `configForms`；
  不同步的话，新内核一启动就是「Failed to load plugins」错误页（实测撞到过）。

■ 为什么两个通用插件必须跟着换

  0.1.7 的客户端**不再提供 `settingsScope` 服务**。人设切换与皮肤的客户端半边如果还在
  `inject` 里等这个服务，就会一直 pending，整套 Web 启动直接报
  「2 entries did not activate … Failed to load plugins」——界面只剩错误页。
  这两个插件在开发目录里早已适配（改用 `configForms` 表单服务），本版把**适配后的构建**
  连同它们的 `package.json`（`dsh.client.inject` 与 peer 范围也变了）一起同步进包。
  两个剧本工作台（剧本批注 / 提示词对照）本来就是按新接口写的，没有这个问题。

■ 另外修掉的一处打包拦路问题

  0.1.7 的运行时闭包清单（内核仓库 `python/sdk-runtime/package.json`）漏了 5 个客户端包
  （`dsh-client-store` / `dsh-client-ui-dockkit` / `dsh-client-ui-primitives` /
  `dsh-client-ui-slots` / `dsh-util-workspace-path`），它们被几十个已入树的 `lib/client.js`
  引用 —— 补齐后打包脚本的缺口扫描才从 `TOTAL MISSING = 5` 变成 0。
  这是**内核仓库该修的东西**，本版为打包在本地补上了。

■ 为什么是主版本号 +1

  本文件顶部的规则写着「主 → 底层 DSH 换代（例如 0.1.5 → 0.2.0）或界面发生大改」——
  这次换的正是底层内核（跨两个 rc：0.1.5-rc.2 → 0.1.7-rc.2）。

■ 升级前请备份（本版第一次启动会做数据迁移）

  · 便携版的数据在 `%LOCALAPPDATA%\DSH-Web`（对话记录、设置、密钥），和程序文件夹是分开的。
  · 0.1.7 读的会话格式比 0.1.5 新，**第一次启动会把老数据往上迁移**（内核里带着
    v0→v1→v2→v3→v4 的迁移链）。迁移是单向的 —— **升级前先复制一份数据目录**，要回退才有退路。
  · 升级方式不变：关掉窗口 → 用新文件夹替换旧的 → 双击启动（记录与设置保留）。

■ 已知问题与边界

■ 插件机制的两个修正（本版顺带修的，两个都是"会让界面整个起不来"的级别）

  ① 插件落点改为**由包名决定**（原来是"一律塞进 node_modules\@dsh-external\"）

       包名 @scope/name  →  node_modules\@scope\name
       包名 name         →  node_modules\name

     为什么必须改：bundles 里的名字是 node **按包名**解析的，落点对不上就等于
     "登记了却解析不到包" → 启动直接失败。小鲸鱼正是不带作用域的包，不修就装不进来。
     诊断.ps1 第 4 节按同样的规则回推落点，否则它会把不带作用域的插件误报成
     "已登记但文件不在"。

  ② 插件删掉后的清理更精确，而且**断链也要能认出名字**

     清理只认"指向 插件\ 的 junction"和旧位置 @dsh-external\ 里的残留；第一方包、
     用户自己 dsh plugin add 装的包一律不碰。关键在断链：插件目录删掉之后，profile 里
     剩下的是**断掉的 junction**，package.json 读不到 —— 旧写法算不出包名，名字就留在
     bundles 里，下一次启动整个失败（这是实测踩出来的，不是推测）。

■ BOM：为什么 .ps1 必须带 UTF-8 BOM

  Windows PowerShell 5.1 读**没有 BOM** 的 .ps1 时按系统 ANSI 代码页解码（中文 Windows
  是 936/GBK）——中文全变乱码；而脚本里 `Join-Path $root '插件'` 这种**中文是参与逻辑的**，
  乱码就等于找不到插件文件夹。本轮给 start-dsh-web.ps1 与 诊断.ps1 都补上了 BOM，
  并在 build-portable.ps1 的打包前校验里加了一条 BOM 检查：缺 BOM 直接拒绝打包。

  ⚠ 维护提醒：编辑器/补丁工具会**静默吃掉 BOM**（本仓库的脚本化编辑就是这样，实测三次
    都被吃掉且不报错），所以改完这两个 .ps1 必须复核；现在打包预校验会兜住这一条。

■ 关于 exe 被重建（以及为什么以后要小心）

  本版**没必要**换 exe：插件功能全在启动器里。但打包脚本 `build-portable.ps1`
  带的 `-SkipBuild` 只跳过 `lib/` 的编译，**并不跳过 exe 的重新打包**，
  所以我按老习惯跑了一次打包，exe 就被重新生成了 —— 哈希随之改变。

  两点后果，记下来免得下次再踩：

    · **exe 打包不是逐字节可复现的**（里面嵌了构建时间戳等元数据）。
      同样的源码重新打一次，得到的是哈希不同的 exe。而"版本记录里写死
      exe 的 SHA256"是核对别人手上那份是哪版的唯一手段 —— 两者放一起，
      就意味着：**只改启动器/说明/插件这类随包文件时，绝对不能重新打包 exe**。
    · 为此给 `build-portable.ps1` 加了 `-ReuseExe`：直接复用 `dist-exe` 里
      已构建好的 exe，只重新组装目录 + 压缩。以后改随包文件就用这个。

  既然 exe 已经变了，我把 v1.0.2 / v1.0.3 修好的东西在新 exe 上**逐条复验**了一遍
  （见下面验证记录），确认没有回退。

■ 新增能力：插件目录

  设计只有一句话：**程序目录下的「插件」是唯一真相源**。

  启动时启动器做三件事（等价于官方 `dsh plugin add` 的收尾动作）：
    1. 扫描「插件」里的每个包，只认声明了 dsh.bundle.patch 的（其余跳过并提示）；
    2. 把它们挂进 profile 的 node_modules\@dsh-external\（用 junction，只存一份）；
    3. 把包名同步进 profile 清单的 bundles 列表。

  为什么不理解插件内部结构也够用：bundles 决定哪些包参与装配；插件包自带的
  cordis.patch.yml 由 loader 自己读；浏览器半边由客户端模块系统按包扫描
  dsh.client 声明发现 —— 三件事都不需要启动器插手。

  用户侧因此得到的能力：
    · 装插件   = 把插件文件夹复制进「插件」，重启
    · 卸载     = 删掉那个文件夹，重启
    · 升级插件 = 用新文件夹覆盖旧的，重启（profile 不用动）

  三个刻意做成这样的决定：

    ① junction 而不是复制：插件只存一份，不会出现"程序里换了、profile 里还是旧的"
       这种版本漂移。junction **可以跨盘**（实测数据目录在 C:、插件目录在 D: 完全
       正常）；建不了 junction 时退回复制（例如目标盘不是 NTFS）。

    ② 不做"只增不删"：插件从「插件」里消失时，它**必须**同时从 bundles 里摘掉。
       残留的名字会让加载器去解析一个不存在的包，结果是**整个界面起不来**。
       这是开发中真踩到的：删掉插件文件夹但没摘名字 → 启动直接失败。

    ③ 改 bundles 用"整段重建"并先做 JSON 校验，校验不过就不写盘。
       profile 清单坏掉等于起不来，所以宁可什么都不改，也不写半份出去。
       （这一条当场救过一次：重建时漏写逗号被校验拦下，文件没被破坏。）

■ 开发中撞出来的一个大坑（值得单独记：看起来能用，其实会删文件）

  插件是用 junction 挂进 profile 的，所以"清理 profile 里的旧条目"看起来就只是
  删掉一个链接。但 Windows + PowerShell 5.1 上，Remove-Item -Recurse 对
  **跨卷** junction 会顺着链接把**目标里的文件全部删掉**：

      junction 在 C:，指向 D: 上的真目录
        Remove-Item -Recurse <junction>           → 目标目录内容被清空
        Remove-Item -Recurse <junction 的父目录>   → 同样被清空
        cmd /c rmdir <junction>                   → 只摘链接，目标完好

  也就是说：便携包放在 D 盘（或 U 盘）、数据目录在 C 盘时，"清理 profile"
  会把「插件」里的真插件文件删干净 —— 用户的插件就这么没了。
  更阴的是：**同卷不触发**，所以在开发机上（数据目录与程序文件夹同盘）
  根本测不出来。这次是在专门做的跨盘测试里撞出来的，代价是一个插件目录
  被清空（已从暂存副本完整恢复，没有实际损失）。

  修复：新增 Remove-PluginEntry —— 是链接就用 rmdir 只摘链接本身，只有真目录
  才用 Remove-Item -Recurse。打包脚本里删除旧 DSH-Web 的地方也做了同样处理
  （否则开发机上指向仓库的 junction 会被打包动作删掉源码）。
  另外补了专门的跨盘回归测试，防止以后再退化。

■ 修了什么

  **现象**：终端工具（pwsh）100% 不可用。随便执行什么命令，都立刻返回：

      [stderr] error: --profile <name> is required
      [exit code] 1

  这句话是 **dsh 自己的命令行参数报错**，PowerShell 绝不会输出它 —— 也就是说
  本该被拉起的 pwsh 没被拉起，被拉起的其实是**本程序自己的 exe**。

  **根因（一处，牵动三个功能）**：程序里有若干地方靠"让 node 去跑一个辅助脚本"
  来实现功能，写法是：

      spawn(process.execPath, [辅助脚本路径, …])

  它假设 `process.execPath` 是一个通用的 node 运行时 —— 在源码方式运行或普通
  node 安装下确实如此。但在**单文件 exe** 里，`process.execPath` 就是这个程序
  自己的 exe，而它的引导**只认 dsh 的命令行**：于是 exe 把"辅助脚本路径"当成
  未知的命令行参数，报 `--profile <name> is required` 后退出，辅助脚本从未运行。

  同一个根因造成三个症状（本次一次全部修好）：

    | 功能 | 走的辅助进程 | 修复前表现 |
    |---|---|---|
    | **终端（shell）** | Windows 沙箱 runner（`dsh-sandbox-windows-acl`） | 工具 100% 失败，报上述文案 |
    | 打开默认浏览器 | 浏览器 opener | 日志报同一句话，浏览器不会自动打开 |
    | 目录选择对话框 | Win32 对话框 worker | worker 提前退出（v1.0.1 已用"改钉网页版"绕过，本次根因也已修） |

  这也解释了为什么**源码方式运行的开发版一切正常** —— 那里 `process.execPath`
  真的是 node。

  **修复一（根因）**：给 exe 的引导加"脚本模式"与"求值模式"。
  现在 exe 被这样调用时，会像 node 一样工作：

      deepseek-harness.exe <存在的 .js/.mjs/.cjs 绝对路径> [参数…]   → 直接跑该脚本
      deepseek-harness.exe --eval <代码> [-- 参数…]                → 直接跑该代码

  判定刻意从严：**必须是"绝对路径 + 真实存在 + .js/.mjs/.cjs 结尾"**（或显式
  `--eval`）。真正的命令行调用是 `web`、`plugin` 这类子命令词，永远不会长得像
  一个存在的绝对脚本路径，所以**现有用法不会被误吃**（已用 `--help` 回归验证）。
  两个模式的 `process.argv` 都与 node 完全一致（浏览器 opener 读的是
  `process.argv[1]`，所以这点必须一模一样）。

  好处：**三个受害功能一个调用点都不用改**，全部自动恢复。

  **修复二（防误读）**：沙箱侧把"被拉起来的其实是 CLI"识别为**运行器失败**，
  而不是把它的 stderr 当成命令输出返回。修复前 exit 1 + 那段文案不匹配运行器
  既有的失败签名（签名是 exit 127 + `windows-acl-run: `），所以失败被静默吞掉、
  伪装成"命令执行结果"，用户和 Agent 都会误以为是命令写错了。现在会明确报
  `SANDBOX_UNAVAILABLE` 并附上原因。

■ 这一版修的是 v1.0.1 的回归

  **现象**：v1.0.1 打包后，本机和其他设备上双击启动都失败：

  **原因（v1.0.1 的预置逻辑写错了）**：cordis.patch.yml 是一份 YAML 文档，顶层

  v1.0.1 用的是「在文件末尾追加一段补丁」，于是在同一文件里出现了两段顶层数组：

      []                        ← 第一个文档：空数组

      - id: directory-picker    ← 第二个文档：再开一个列表 → 语法错误
        disabled: true

  YAML 解析器读到第二段的开头就报 document separator 错误，配置根本加载不了，
  程序启动即失败。

  **为什么 v1.0.1 自测没发现**：我当时的测试顺序是「程序先生成模板、再追加补丁」，
  那份文件里只有我追加的一段，恰好是合法的；而全新设备上的真实顺序是
  「启动器先写补丁、程序之后又补上模板 `[]`」→ 变成两段 → 崩。
  换句话说，**测试环境与真实首次启动的写入顺序不同，掩盖了这个 bug**。
  教训：这类"改配置文件"的逻辑，必须在"文件不存在"的全新路径上测，而不只是在
  已有文件上测。

  **修复**：启动器不再追加，改为**整份重写** cordis.patch.yml —— 单一文档、
  单一顶层数组、单一数组元素集合，从结构上消除"两段文档"的可能：

      # 注释若干行（说明本文件由启动器重写、请勿手工编辑）
      - id: directory-picker
        disabled: true

      - insert:
          - id: directory-picker-browse
            name: '@deepseek-ai/dsh-host-directory-picker-browse'
          - id: directory-picker-browse-surface
            name: '@deepseek-ai/dsh-client-ui-directory-picker-browse'

  并保留内容比对：**只有内容不同才写盘**，重复启动不会改动文件（两次启动后
  文件大小与写入时间完全相同，已验证）。

  **升级后无需手工处理**：启动器会在启动前把损坏的文件整份覆盖为正确内容 ——
  也就是说直接换上新版启动器即可，不必删除 profile、不必重装。
